# Study workbench

The application presents this workbench as LCA calculations. A calculation project is the user-facing name for a Study, which can contain scenarios, calculation runs and reports. Method declarations retain their scientific study terminology.

Platform owns authenticated `/studies`, `/study-report?id=<reportRevisionId>&hash=<contentHash>` and `/study-share?id=<shareId>`. Valid existing report/share links without a selector retain V4. The explicit advanced and method forms add exactly one `api=5` or `api=6`; ID/hash/family fields are validated before requests, and duplicate, malformed or unknown query fields fail. `reportHref` / `shareHref` generate these stable same-object links; the report identity and share-result/recipient links retain their selected family. The selector binds the resource protocol, never a backend URL, credential or permission. Existing AuthGuard, application admission, Supabase session and layout remain authoritative. `/studies?id=<studyId>&view=<overview|model|results|reports>` uses the shared finite route-view registry. A reviewer can open an exact report independently of core Study access; a named share performs only resource-action, projection and download calls for that share.

## Service and ownership boundary

All API calls stay in `src/services/study`. The service invokes `app_lca_study`, snapshots the admitted identity generation, captures the current bearer session and discards responses after admission, actor or captured-bearer changes, including a switch away and back to the original actor. Mounted views also invalidate synchronously on bearer changes, including same-actor client switches; the auth callback performs no asynchronous work. A concurrent token refresh can therefore require a fresh read. No authentication credential is persisted by this feature. Pending mutation bodies are held only in the bounded same-tab journal described below. Exact contained Edge V2, V3, V4, V5 and V6 public codecs live in `vendor/study-contract`; their unchanged manifests and licenses record producer identity. The adjacent Platform `.d.mts` adapters only resolve the original declarations. Tests verify artifact provenance separately from application code coverage. Vendored artifacts are protocol inputs, not a second editable schema.

The retained V2 consumer deliberately adopts already Main-qualified Edge source `439f8112a8f9945479c63ffaa8cfe688e9d20216`, manifest SHA256 `0cfe9a2d3c957a005a6b8045b3f8df0cea9b3e852af7a49f706e3b35a798b0c1`, for archive acknowledgement validation. Its wire schema2.0.0, request/response schema bytes and declarations are unchanged. Core and original-V2 recovery accept archive success only with `archived` status and exactly `expectedRevision + 1`; a mismatched success retains the original ambiguous intent. No archive UI or local parallel schema is introduced. V3–V5 artifacts and renderer1/2/3 bytes remain unchanged, and valid historical journal envelopes retain their original identity.

Each request and response passes the owning codec's strict parser and operation-specific bindings. Frozen JSON artifacts additionally require exact byte size and SHA-256 before decoding. Narrow presentation guards read only the supplied model/fact fields; the browser does not recreate model fingerprints, calculation contracts, numerical analysis, review policy or authorization. Legacy solve, comparison, hotspot and latest-dataset services are not Study sources.

## Views and editing

Overview reads the selected frozen StudyRevision's goal, functional unit, boundary and exact source identities. Model/evidence reads a selected preparation's `inputArtifactRef` and shows its frozen instances, exchanges, connections, cutoffs, source documents and quality findings. The process display is bounded to 64 instances; full supplied exchanges remain in the paged table. Results show exact Worker-provided canonical values, units, coverage, provenance and comparability. Null remains unknown; partial coverage is a characterized subtotal. Supplied facts never become a browser-computed ranking.

Lightweight editing is restricted to eligible non-reference exchange amounts. A frozen predecessor must belong to the displayed preparation. Current V2 capabilities and V4 `corePermissions.write` gate the workflow; each actual operation is still reauthorized by the server. Creating a new ScenarioRevision copies the predecessor overrides and replaces only the selected amount override. Preparation uses the exact new scenario revision/hash, then successful preparation permits freeze with expected revision/hash and submission of a Run with its exact input hash and calculation-contract reference. Frozen predecessors are not saved or changed. Unsupported reference, parameter or provider editing has no control.

Writes persist the exact parsed request/schema/request ID/idempotency key before dispatch in an actor/client/origin/workflow-bound `sessionStorage` journal. Verified current `getClaims()` identity and the existing admission generation bind both dispatch and explicit recovery. Recovery captures actor, OAuth client, bearer and admission generation before reading the journal and retains that exact identity through dispatch; asynchronous journal/claims work cannot rebind the original payload or key to a replacement session. A synchronous Auth listener invalidates a switch away and back, and every temporary listener is released. One unresolved request blocks that workflow/resource, not unrelated Studies. UI scenario/preparation/freeze/Run stages all pass the same `study:<id>` context. No credential, automatic replay or background job queue is stored. A same-tab reload offers explicit recovery of the exact original request; server state, receipts, retention and current rights remain authoritative. The workbench retains the recovered request/result for the admitted Study mount, including recovery from its header. Reselecting the original frozen preparation and non-reference exchange restores the exact predecessor, amount, new scenario and preparation only after matching original overrides, source revision/hash, profile and contract; fresh reads use recovered IDs, never a latest resource. Preparation/freeze recovery permits the next explicit stage without replaying a completed stage or inventing a key. A foreign selection or changed source fails closed; identity/Study changes discard this ephemeral handoff.

V5 report/share workflows use independent `report5:<id>` / `share5:<id>` keys; existing V2/V3/V4 keys and stored bytes remain unchanged. The original request schema selects recovery and current retirement checks, and a cross-family workflow binding fails before dispatch. No stored intent is migrated or rewritten into another API version.

The journal allows at most eight current/retired records and 256 KiB per current record. Its schema, checksum, operation metadata, identity, origin, workflow and known resource bindings are validated before any recovery POST. Corrupt, unsupported and impossible-future records fail closed and remain inspectable; elapsed client time never expires a valid intent or mints a new key. Session storage and its checksum detect accidental corruption within browser-owner trust; they do not authenticate a malicious browser owner or same-origin script. The journal lasts only for that browser tab's session and is not cross-device durable state.

Persisted `dispatching` marks crash/reload uncertainty. Transport failures, timeouts, invalid responses, 5xx and earlier unfinished dispatches set sticky `everAmbiguous`. A later FORBIDDEN/conflict does not prove an earlier attempt uncommitted. A validated success for the exact request clears the pending record. Only a never-ambiguous, validated nonretryable rejection offers explicit local retirement: the current target is read again under the same identity, and the original request/key/audit identity is retained in a retired record before a fresh intent is allowed. Retirement is not server cancellation, undo or a claim of no server effect. Identity changes hide other actors'/clients' records and clear visible response state.

## Reports, review and shares

Report controls use explicitly selected V4, V5 or V6 resource actions and current report state. A V5 request/response uses the immutable Edge5.0.0 codec and exact selection bindings; denial, unavailable capability or wrong schema never triggers a V4 fallback. Report-only V5 actions do not authorize a core Study read. Component and query identity includes the family, so a family change suppresses a late older projection. The legacy Study reports/results lists remain their V3/facts.v1 consumers; initial advanced-report entry is an exact CLI-created report/share link, without client-side page merging or an analysis wizard. Comments bind revision/content hash; decisions bind the exact predecessor review and declare internal review, with no independent-certification claim. The UI disables author self-approval and the server enforces the policy. Explicit OAuth client delegation binds one decision, predecessor, content and expiry; the browser does not invent human approval or consume delegation as a direct actor.

Finalization sends the exact revision, content hash, review-state hash, profile and accepted review IDs from current state. Exports bind current finalization/review state. V4 sends renderer1.0.0/view.v1; V5 sends renderer2.0.0/view.v2; V6 sends renderer3.0.0/view.v3, with the selected client retained through history, mutation and recovery. Named sharing binds one exact report/export, registered recipient identity, summary disclosure policy and expiry. Revocation queries actions and metadata for the selected share through the same protocol family, verifies its report revision/content hash, and uses that share's current `share.revoke` action rather than a report-level permission. Share and review-delegation selections remain independent. Query identity includes family, report/hash, share and refreshed history, so replaced or late metadata cannot enable a different target. Roles offered for membership come only from `allowedMemberRoles`; there is no user discovery or roster endpoint. Every mutation remains subject to server authorization and CAS.

The report projection and its recorded validity/review snapshot are displayed separately from current online state. Platform's private preview entrypoint shares the validated content/table/chart/escaping implementation with the standalone renderer, but supplies honest online framing without an export ID, receipt or verification claim. The portable export API uses its exact artifact version. Online preview explicitly dispatches retained1.0.0/2.0.0 and method3.0.0 recorded projections without changing their version or bytes. Its generated chapter links explicitly target `about:srcdoc#<section>` so native keyboard/mouse navigation stays in the same sandboxed report document instead of resolving against the host application URL. This online-only binding adds no base element or script and preserves the existing CSP/sandbox; portable export markup and artifacts retain their own document-relative links. Renderer3.0.0 exports require view3 with its mandatory method summary and reject old view1/view2 projections. Retained view1/view2 online content/resources come from the exact original source44da renderer2 package; independently pinned P2/P3 packages and historical exports are not repinned or regenerated for preview. The fixed English report reading language remains governed by the renderer contract; app controls use every active locale catalog.

Named recipients receive only `share.view` and `share.download` projections. They are not given core Study tabs, model/facts reads, source membership or an anonymous URL. Download reauthorizes and checks exact bundle size/hash before creating a temporary download of the persisted V4 `lca.study-export-bundle.v2` V5 `lca.study-export-bundle.v3`, or V6 `lca.study-export-bundle.v4` JSON bytes through the selected client. It preserves the reference's `application/json` media type and uses a `.json` filename. The captured actor/client/bearer/admission identity is reverified after asynchronous SHA-256 and immediately before the DOM click; stale identity prevents the effect. Temporary object URLs are released even when browser dispatch fails. This integrity check is not represented as independently trusted receipt verification. Revocation/expiry governs subsequent online access and cannot recall downloaded copies.

## Method authoring

The reports tab defaults to its historical V3 list. Selecting “Method assessments and reports” explicitly opens the V6 workspace; the Study landing page also offers exact V4/V5/V6 report-link selection. Method authoring requires the already authorized Study's current core write permission plus the V6 runtime/operation capabilities. Report-only and named-share links retain their independent resource rights and never mount this core workspace.

The contained Edge6.0.0 facade is pinned to source `c322ec2d018dcd0cbb66549ecbddfbe8b10dc59b`, manifest SHA256 `003deb096baa38b7ff6cb5474815ea0eb92bb4c6d188bb6c27f81448026d0427`. Its request/response schema bytes retain the earlier a33a5fb interface; declarations, all33 operations and the three owner readers retain their exact77e bytes. The corrected owner draft parser rejects non-scalar Unicode throughout report create/save content before dispatch or journaling; paired Unicode is preserved. Platform adds no parallel Unicode or report-domain policy. Earlier a33/77 artifacts and their proof are retained as history. V6 reads and writes retain a temporary identity listener across asynchronous preparation and response validation. The captured identity is reverified after validation, and the synchronous fence runs immediately before journal removal after its checksum read. Every V6 response passes the owner's asynchronous `validateResponseContentForRequest` before success disclosure or journal clearance; config hashes and evidence content hashes/byte sizes come only from owner helpers. `report6:<id>` and `share6:<id>` preserve original V6 request envelopes and cannot recover through V4/V5. Core method creation shares the existing `study:<id>` pending-intent boundary, so an unresolved same-Study write blocks a new method write. Each explicit mutation click captures one idempotency key before its command closure; the first local retry reuses that original payload/key rather than allocating a replacement.

Evidence controls record exact statements and citations as `recorded_unverified`. An evidence read is current-server-authorized and then parsed against its exact recorded bytes by `parseMethodEvidenceForRecord`; selecting it copies the exact reference into the declared config. The fixed public module identity/requirement names come from the retained owner metadata. Product role, declared-mass basis, phase and category-rule declarations never establish applicability or professional approval. Assessment submission captures the current actor/client/bearer/admission fence through `prepareMethodRequest` before awaiting `methodConfigHash`, then retains that same fence into dispatch; selected assessment reads use exact typed task/actions and original assessment identity. Cancellation requires that selected assessment's current `task.cancel` action. There is no automatic polling, replay or version fallback.

`readMethodArtifact` retains the captured actor/client/bearer/admission fence across the authorized artifact read and asynchronous owner parser, and rechecks it before returning parsed content. `parseMethodFactsForAssessment` validates the authorized artifact's byte size/SHA-256, closed owner schema and recorded assessment/source binding before any claim selection. The workspace retains all20 requirement states,25 category roles,58 supplied catalog facts and the complete source/normalisation/weighting/qualification fields independently of authored narrative. Null stays unknown; source gaps, unavailable N/W, recorded-unverified evidence and false qualification flags remain explicit. The complete selected-factor list is available only through its authorized facts artifact. No browser numerical analysis, factor selection, ranking, complete-PEF or professional-approval override is implemented.

New report claims copy the selected catalog's exact fact ID, canonical value, unit and facts reference. `parseMethodReportContentForRevision` reopens exact stored content without dropping sections, tables, charts or limitations. Save binds the selected revision; freeze binds the saved revision and hash and is disabled while local edits differ from that saved draft. An explicit successor keeps the frozen predecessor and sends its exact parent ID. Distinct authored claims may share one fact. Selecting another fact preserves every retained claim and allocates an ID that cannot collide with existing claim IDs. Fact deselection removes only that fact's authored references; mandatory method disclosure remains separate. Report save/freeze use current resource actions, while creating a successor additionally requires core write and the V6 creation capability. Existing review/finalization/export/share controls preserve exact V6 state, hashes, renderer3/view3 and bundle4.

These source/fixture controls do not establish actual registered Study/native execution, current production permission, scientific validity or professional evidence. Parent-owned installed CLI/API/DB/native/Storage/browser qualification and supported delivery/integration remain separate requirements.
